# Root image flash and full install — 2026-10-29

Donor `MRV8IJJVPRYTS4UG` was flashed with the pinned `neutron.img` and then
given the full app and module set. The write was the first time the rooting
slice's flash button (`#fb-flash` → `FASTBOOT.flashBoot()`) has ever been
pressed, by a person or by a script.

This is a record of the run, not of a recovery. The image was a known-good
published one and the phone was healthy throughout.

## What was flashed

`neutron.img` from `catalog.json` (`1.1.1-flip2`), the same pin the page has
always enforced:

```
size   25165824   (0x1800000, exactly the boot partition size)
sha256 31237917ef51fa6e7ee588da1cfc84bb378859de2d49681fdd4f84290841d3c1
```

The page will not enable the flash button until `VERIFIED['neutron']` is set
by a WebCrypto SHA-256 match against that pin, so nothing local or unpinned
can reach this path.

## Getting into fastboot

`adb reboot bootloader` does not stop at the bootloader on this hardware. The
route that works is the preloader handshake: catch `0e8d:2000` on
`/dev/ttyACM0` and write `FASTBOOT` at 115200. This run used
`/tmp/preloader-fastboot.py`, which is the one exception granted for donor
recovery; the reply was `READYTOO` and the bus re-enumerated as `0e8d:201c`.

The health gate was read before any write:

```
product:               gflip6
serialno:              MRV8IJJVPRYTS4UG
partition-size:boot:   1800000        (25,165,824 bytes)
unlocked:              yes
```

Serial checked, not assumed — a second phone on the bus would have shown up
here and nothing would have been written.

## The flash, driven from the page

The rooting slice was opened through its `erase` gate and its own buttons were
clicked over the Electron debug port (`/tmp/wiz-root.js`, not committed).
Because the phone is already unlocked, `#fb-pick` read `unlocked: yes` and went
straight to the flash stage, skipping `#fb-unlock` entirely — no second unlock
was sent, which is the one thing on this slice that would have erased the
phone.

What the page logged:

```
Claimed fastboot interface.
serialno: MRV8IJJVPRYTS4UG
unlocked: yes
download:01800000 (25165824 bytes)
```

`01800000` is the DATA size header the bootloader expects, and it matched the
image length exactly, so the DATA phase ran. Then `flash:boot`, then reboot.

After the reboot the partition hashed to
`31237917ef51fa6e7ee588da1cfc84bb378859de2d49681fdd4f84290841d3c1` — the pin,
byte for byte.

**This differs from the earlier factory-page run.** That one wrote a copy that
was already on the partition, so a broken write would have been invisible. Here
the partition content actually changed (`40ef8d56…7cedd6a5` → `31237917…`), so
the write demonstrably moved 24 MiB of new bytes into `boot` and the phone
still booted. What it still does not prove is recovery from a *bad* image.

## The install — and why it went over host adb

The page's step-5 install could not claim the phone: its WebUSB ADB path
reports "Another program is using the phone: the adb server on this
computer." Killing `adb-server` was not authorised, so this run used the
fallback the plan allows — the same files, the same scripts, driven over host
adb instead of WebUSB.

That is a real limit and should be read as one: the *payload* path is proven,
the *transport* the page uses for step 5 is not. `install.sh` and `verify.sh`
themselves are unchanged and are what ran.

The push set was built by the same logic the page uses
(`PIPE.buildPushSet`): the installer zip unpacked into its four module zips,
`launcher4.apk` and `nullkeyboard.apk` taken from the zip payload, the Tag
Drawer module rebuilt around the fresh F-Droid APK, browser downloads renamed
to the fixed names — 14 files.

## The Tag Drawer module needs a reboot

The first `verify.sh` after the install failed one check:

```
FAIL: Tag Drawer installed
```

The APK was in the module but not yet mounted — the module places it at
`/system/app/PixelTagDrawer/PixelTagDrawer.apk` during mount, which has not
happened in the session it was written. After a reboot `pm path
com.iwadjp.pixeltagdrawer` resolved to `package:/system/app/PixelTagDrawer/PixelTagDrawer.apk`
and the check passed. `verify.sh` run immediately after `install.sh` will
always fail this one; the page's own order (install → reboot → verify) is the
correct one.

## The bug this run caught

After the flash, the rooting slice's log pane stopped at `unlocked: yes` while
a second `download:01800000` line appeared in the *factory* slice's log. The
factory page sets `FASTBOOT.log` to its own pane when it connects and nothing
restores it, so a rooting flash run after a factory run wrote its download and
flash lines into the other slice's `<pre>`.

Fixed in `wizard/pages/js/main.js` by setting `FASTBOOT.log = log;` at the top
of the `#fb-pick` handler (`e067082`). The flash itself was unaffected — only
the log routing was wrong — but a person reading the pane would have thought
the write had stalled.

## What this run proves, and what it does not

It proves the rooting slice's flash path works for real: the `erase` gate, the
serial and lock reads, `FASTBOOT.flashBoot()` sending 24 MiB with the legacy
DATA header, `flash:boot`, the reboot, and a boot partition whose hash is now
the pinned image — with different content going in than what was there before.
It also proves the full install set lands and verifies on the other side.

It does not prove: the page's WebUSB ADB transport for step 5 (host adb was
used), recovery from a deliberately bad boot image, or anything about a phone
that is already unbootable. No wipe, no relock, no `unlock_critical` — the
bootloader is still unlocked and verified boot is still `orange`, as the page
says it should be.
